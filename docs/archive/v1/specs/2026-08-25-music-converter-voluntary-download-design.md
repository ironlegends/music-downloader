# Design specification: voluntary browser downloads and launcher security

Date: 2026-08-25
Status: Approved for TDD planning; no implementation in this step
Base: e9b90064769865c1c65397269f44852a2c2419d9
Branch: feat/launcher-safety-semver

## Objective and boundaries

Restore a genuinely functional, voluntary download experience through scripts that the user runs on the SpotMate page, without reactivating local launcher conversion. The local capability remains disabled at all times and POST /api/queue/start continues to return HTTP 503.

The current public service requires a Turnstile check on /getTrackData, and /convert expects track values produced by the page. A raw call from the local client currently returns HTTP 422. This design does not bypass Turnstile or CAPTCHA, extract any token outside the page, or turn this remote behavior into a launcher contract.

Implementation scope:

- server.js and test/server.test.js for local boundary security.
- script2.txt and tests/test_script2.cjs for sequential, voluntary conversion tied to the SpotMate DOM.
- script3.txt and tests/test_script3.cjs for explicitly triggered downloads.
- script_complet.txt and tests/test_script_complet.cjs for the all-in-one experience.
- README.md, docs/architecture.md, CHANGELOG.md, package.json, and relevant metadata tests.
- script1.txt only if a test proves a strictly necessary change is essential. Without that evidence, it remains unchanged.

Inert diagnostics, the anti-secret guard, and older documents are preserved. No real token, cookie, secret, or audio URL is included in the repository or fixtures.

## Options considered

### Option A — Voluntary browser helper and local hardening (selected)

Scripts run only on https://spotmate.online/en1. The existing page remains responsible for submitting /getTrackData, presenting Turnstile, and producing hidden track inputs. The helper observes the DOM after this manual step, reads each hidden value within the current conversion closure, calls /convert with the page context, polls asynchronous tasks, and exposes only results without secrets. Downloads start only from the panel after a per-track click or a click on Download all.

At the same time, the local launcher is hardened without being reactivated: bind to 127.0.0.1, require a local Host and the actual port, require same-origin Origin for API POST requests, bound JSON and SSE, contain audio files, and start processes without a shell.

**Benefits:** respects the human Turnstile flow, uses values produced by the site without reconstructing them, provides observable user control, and maintains the fail-closed local boundary.
**Cost:** requires a loaded SpotMate page, manual verification, and live browser validation; the helper depends on the DOM and visible public contract.

### Option B — Reactivate the raw local client and /api/queue/start

The launcher would call /getTrackData and /convert directly from Node and reactivate the local queue.

**Benefits:** uniform UI integration and apparent local automation.
**Rejected:** the raw client lacks Turnstile context and the track values generated by the page, and currently receives 422. This would push toward bypassing verification, make cookies/CSRF opaque to the local server, and contradict the fail-closed contract. Explicitly out of scope.

### Option C — Hidden iframe, automatic browser, or token relay

The launcher would open a hidden iframe, automate verification, or relay cookies/tokens to Node.

**Benefits:** fewer visible manual steps.
**Rejected:** not voluntary, fragile under browser policies, could become a CAPTCHA/Turnstile bypass, and conflicts with the rule against automatic hidden iframes. No token may leave the page.

## Architecture decision

Option A is selected. The three scripts share a data protocol without sharing a secret:

~~~text
Page https://spotmate.online/en1
  -> user submits the URL in the existing SpotMate form
  -> user completes Turnstile
  -> DOM produces hidden track inputs
  -> script2 waits for and validates these inputs, then waits for the Start conversions click
  -> sequential /convert, then /tasks/{id} if task_id or taskId is returned
  -> non-sensitive results only
  -> script3 or the integrated panel waits for a download click
~~~

script2.txt installs the conversion panel and owns these logical functions within its execution scope:

- isAllowedSpotmatePage accepts only HTTPS origin https://spotmate.online and path /en1 or /en1/.
- collectTrackInputs accepts at most 100 non-empty hidden inputs produced by the DOM, associates each input with a stable identifier, and rejects any track without a hidden value.
- submitExistingSpotifyForm(url) uses the existing SpotMate form (form action /getTrackData or its existing URL field), without creating an iframe or parallel request. The entered URL must be a valid HTTPS Spotify URL.
- waitForTrackInputs(signal) observes DOM mutations after submission and allows the user to complete Turnstile. Cancellation disconnects the observer.
- readPageCsrfToken() reads the dynamic token from the meta tag or page cookie at request time. The token is a local request variable, is never logged, and is never placed in window, a result, the panel, or a global variable.
- convertTrack(track, signal) posts the page-produced hidden value to new URL('/convert', location.origin), uses credentials same-origin, sends only { urls: track.value } in the body, and reads the dynamic CSRF token into X-CSRF-TOKEN. Any non-OK response is terminal and is not retried; the response must be application/json before response.json() is called. It accepts a valid final HTTPS URL or a non-empty task_id/taskId.
- pollTask(taskId, signal) waits 4500 ms, then calls new URL('/tasks/' + encodeURIComponent(taskId), location.origin) sequentially up to 40 times (with 4500 ms before each of the 40 polls), until it gets a valid final HTTPS URL, an immediate terminal error payload, or another terminal state.
- convertSequentially(tracks, signal) starts only after an explicit click, processes one track at a time, and waits 2000 ms between starts. Codes 403, 419, 422, 429, and 500–599 become terminal errors without automatic retry; network or schema errors are also terminal.
- cancelConversions() calls AbortController.abort(), stops polling, marks the run as cancelled, and checks this marker before starting the next track.

The panel exposes Load Spotify URL, Start conversions, and Cancel. If inputs are already present, the load button is optional; otherwise the panel asks for the URL, submits the existing form, and waits for the DOM. The script never converts on installation. Clicking Start conversions is the only transition to the conversion state.

script3.txt consumes non-sensitive results and installs a download panel. It accepts only values where new URL(value).protocol === 'https:'. Each track has its own explicit button; Download all walks the URLs in order with 1500 ms between starts. A user click activates the link; no hidden iframe is created automatically. No download starts when the script is installed.

script_complet.txt uses the same state machine and observable functions in one standalone script. It does not assume script1.txt, script2.txt, or script3.txt has run, and does not duplicate any token in global state. script1.txt remains a historical identifier-reading tool and does not authorize conversion.

## Local contract remains fail-closed

CONVERSION_CAPABILITY remains frozen with enabled: false, code launcher-local-conversion-disabled, and its current message. GET /api/status continues to expose this capability. POST /api/queue/start checks the capability after necessary boundary checks, returns 503, and never calls queueManager.start, regardless of the body. No downloader or additional queue hardening is required while this route remains 503.

The server must enforce:

- Listen exclusively on 127.0.0.1.
- Accept only Host: localhost:<port> or Host: 127.0.0.1:<port>, using the actual assigned port.
- Require every API POST to have an Origin equal to http://localhost:<port> or http://127.0.0.1:<port>; never return Access-Control-Allow-Origin: *.
- Reject JSON whose type is not application/json or whose UTF-8 size exceeds 65536 bytes, without buffering an unbounded body.
- Limit /api/events to 8 simultaneous SSE clients; reject the ninth without counting it.
- Decode the audio identifier without leaking an exception, then serve only a real file whose resolved path remains under the resolved destinationDir.
- Validate and create the candidate folder before assigning currentConfig; never replace a valid configuration with a failing value.
- Open folders and browsers with spawn or execFile, shell: false, and separate arguments. Do not interpolate a command.

The threat model covers foreign websites and malformed third-party inputs: forged Host/Origin, oversized JSON, encoded paths, files outside the folder, invalid task IDs and final URLs, unexpected HTTP responses, and the SSE limit. A malicious local process is out of scope; loopback binding is not presented as a defense against it.

## Versioning and documentation

This is a compatible feature: package.json.version moves from 1.0.0 to 1.1.0. CHANGELOG.md adds a [1.1.0] - 2026-08-25 entry describing the voluntary helper and launcher hardening. README.md and docs/architecture.md explicitly distinguish the browser helper from the local launcher and state that /api/queue/start is not reactivated. Older specification and plan documents remain unchanged.

## Acceptance criteria

1. Tests for script2.txt show one POST /convert per track, no /api/queue/start request, immediate refusal without retry for codes 403/419/422/429/5xx, rejection of a /convert response without application/json, support for camelCase taskId, error handling for payload.error without retry, direct success, task_id/taskId polling bounded to 40 polls at 4500 ms, the 100-track limit, 2000 ms delay, and cancellation before the next track.
2. Tests show that synthetic token and cookie values appear neither in logs, window.fetchResults, nor the panel; the anti-secret guard passes and no real value is added.
3. Tests for script3.txt show no download on installation, individual click behavior, sequential Download all at 1500 ms, HTTPS-only acceptance, and no hidden iframe.
4. Tests for the complete script prove the same sequence without a dependency on script1, plus use of the existing form, waiting for the DOM, and explicit buttons.
5. Server tests prove loopback binding, Host/port, Origin, no CORS *, JSON limit, SSE limit, audio containment, atomic configuration, shell:false arguments, and unchanged 503 behavior for /api/queue/start.
6. package.json has music-converter, 1.1.0, and private: true; README, architecture, and changelog describe the contract without promising local conversion.
7. Manual browser QA on https://spotmate.online/en1 with playlist https://open.spotify.com/playlist/688Vx1ajrCS05YwFZ4zo3Q confirms the voluntary flow: the user completes Turnstile, clicks to convert, then clicks to download. Evidence retains only counts, states, HTTP statuses, bounds, and timings; it discloses no token, cookie, or audio URL.

## Limits and gates

Live evidence depends on the public site, its DOM, and manual verification; it is not simulated by a fixture and does not authorize bypassing controls. The planning worker performs no network access, commit, push, tag, release, or PR. Implementation must remain sequential because all three scripts and their tests share the same protocol. A contradiction that prevents this design or the ability to produce an executable TDD plan is the only planned escalation condition.
